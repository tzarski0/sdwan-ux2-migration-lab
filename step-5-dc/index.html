Step 5: Migrate the DC from UX 1.0 to UX 2.0¶

All the preparation so far leads to this moment:

  • the UX 2.0 configuration groups and policy group are ready (Step 0),
  • the new sites exist in the network hierarchy (Step 2),
  • the UX 1.0 policy accepts the DC at its new site ID (Step 3),
  • the UX 2.0 topology is active for the new branch sites (Step 4).

Now you can start moving sites to UX 2.0. You don't have to move everything at once: pick a few sites to start with, migrate them, check that they work, and then continue with the rest. In this lab you start with the DC, then move the branches in Step 6.

Migrating a site takes three steps:

  1. Detach its routers from the UX 1.0 device template.
  2. Deploy them with the UX 2.0 configuration group, using the new site ID. For the DC, that's configuration group dc and site ID 110.
  3. Deploy the policy group policy_group to them.

Expected: a brief control and data connection flap

Changing a router's site ID resets its control connections and data plane tunnels. When each router gets its new site ID, you'll see a short drop of its control and data connections. This is expected, and the connections come back up on their own.

Rolling back

If you hit a problem with a migrated site, rolling it back is simple: attach its routers back to the old UX 1.0 device template, using the CSV you exported, and set the site ID back to the old value. The UX 1.0 policy still covers the old site IDs, so the site returns to its previous state.

Detach from the device template¶

  • Go to Configuration → Templates. Click … next to the DC device template and select Export CSV. Keep this file: it is useful if you need to roll back. Then click … again and select Detach Devices.

  • Select both DC routers, move them to the right and click Detach.

  • Wait until the detachment succeeds.

Detaching doesn't change the router's configuration

Detaching a device template does not modify the routers' configuration. The routers keep running exactly the same configuration as before, so traffic isn't affected. They are just no longer managed by a device template. The configuration changes only when you deploy the configuration group in the next section.

Deploy the configuration group¶

  • Go to Configuration → Configuration Groups. Expand the dc group and, next to Associated, click Add.

  • Select Manual association and click Add Devices.

  • Select both DC routers and click Save.

  • Click Deploy for the dc configuration group.

  • Fill in the variables for dc-edge1. Set Site Id to the new site ID 110.

    System IP Host Name Site Id vpn1_gi3_ip vpn1_gi3_mask vpn1_bgp_neighbor_ip
    10.0.0.11 dc-edge1 110 192.168.10.1 /30 192.168.10.2

  • Select the dc-edge2 router from the Chassis Number list at the top.

  • Fill in the variables for dc-edge2. Set Site Id to the new site ID 110. Click Next.

    System IP Host Name Site Id vpn1_gi3_ip vpn1_gi3_mask vpn1_bgp_neighbor_ip
    10.0.0.12 dc-edge2 110 192.168.10.5 /30 192.168.10.6

  • Click Preview CLI to compare the UX 1.0 configuration currently on the router with the new UX 2.0 configuration.

    Expected differences

    The QoS configuration is removed, because no policy group is assigned to the router yet. The router also loses its data policy until the policy group is assigned. Both come back in the next section.

  • After reviewing the configuration, click Deploy. On the next screen, click View Deployment Status and wait until the configuration group is deployed.

Deploy the policy group¶

  • Go to Configuration → Policy Groups. Expand policy_group and, next to Associated, click Add.

  • Click Next, select both DC routers and click Next.

  • Click Associate Devices.

  • In the pop-up window, click Provision Devices.

  • Select both DC routers and click Next.

  • Click Next, then Preview CLI. Verify that the QoS and application visibility settings are added back to the configuration.

  • Click Deploy, then View Deployment Status, and wait until the policy group is deployed.
