Step 3: Update the UX 1.0 Centralized Policy for the New Site IDs¶

During migration, some sites run on UX 1.0 and some on UX 2.0. Before moving any router, make sure the UX 1.0 centralized policy keeps working for branches that are still on UX 1.0 after the DC gets its new site ID.

The current policy¶

The active centralized policy centralized_policy has two parts:

  • Control policy branches-hub-and-spoke, which builds the hub-and-spoke topology.
  • Data policy traffic-data, which sets the forwarding class from the DSCP value (46 → voice, 34 → business, 8 → scavenger).

The control policy uses the two site lists you noted in Step 1: dc (site ID 10) and branches (site IDs 20-99).

%%{init: {"flowchart": {"wrappingWidth": 400}}}%%
flowchart LR
    D["DC<br/>site ID 10"]
    C(["Controllers"])
    P["control policy<br/>branches-hub-and-spoke<br/>accept: site-list dc<br/>reject: everything else"]
    B["Branches<br/>site IDs 20-99"]
    D -- "TLOCs and routes" --> C
    C -- "out, to site-list branches" --> P
    P -- "only DC TLOCs and routes" --> B

In CLI form, the policy that the Controllers run looks like this:

policy
 control-policy branches-hub-and-spoke
  sequence 1
   match tloc
    site-list dc            ! (2) match: which TLOCs are accepted
   action accept
  sequence 11
   match route
    site-list dc            ! (2) match: which routes are accepted
   action accept
  default-action reject
 lists
  site-list branches
   site-id 20-99
  site-list dc
   site-id 10
apply-policy
 site-list branches         ! (1) apply: which routers get the filtered view
  control-policy branches-hub-and-spoke out

Two different site lists¶

The same policy uses site lists in two places, and they mean different things:

(1) Site list in apply-policy (2) Site list in a match entry
Question it answers Who receives the policy? What is accepted?
In this policy branches (20-99) dc (10)
Effect The Controllers filter what they advertise out to routers at sites 20-99. Only TLOCs and routes that originate at site 10 pass. Everything else hits default-action reject.

The result: each branch only learns TLOCs and routes from the DC, so it builds tunnels only to the DC and sends branch-to-branch traffic through the DC. Routers that are not in the apply list (the DC itself) are not filtered and learn everything.

What breaks during migration¶

In Step 5 the DC routers move to the new site ID 110. If the policy is left as it is:

%%{init: {"flowchart": {"wrappingWidth": 400}}}%%
flowchart LR
    D2["DC on UX 2.0<br/>site ID 110"]
    P["branches-hub-and-spoke<br/>match site-list dc (10)"]
    B["Branches still on UX 1.0<br/>site IDs 21-23"]
    D2 -- "TLOCs and routes" --> P
    P -- "✗ rejected: 110 is not in site-list dc" --> B

The branches would lose every TLOC and route from the DC, because 110 doesn't match site list dc. Branch traffic to the DC would stop.

The target policy¶

Add a new match site list, ux2-dc (110), so the policy accepts the DC at both its old and its new site ID. The apply list stays branches, so the policy still only applies to branches that are on UX 1.0.

control-policy branches-hub-and-spoke
 sequence 1
  match tloc
   site-list dc
  action accept
 sequence 11
  match tloc
   site-list ux2-dc
  action accept
 sequence 21
  match route
   site-list dc
  action accept
 sequence 31
  match route
   site-list ux2-dc
  action accept
 default-action reject

Green lines are added in this step. Sequence numbers are assigned by SD-WAN Manager and may differ in your CLI preview.

You also create site list ux2-branches (120-199) for the new branch site IDs. You don't use it in this step. It's ready for later, for example if the UX 1.0 policy needs to reference migrated branches.

Why not just change site list dc to 110?

During the migration both DC site IDs are in use: not every DC router moves at the same moment, and you may need to roll back. Accepting both 10 and 110 keeps branches connected to the DC at every point of the migration.

Tasks¶

  • Go to Configuration → Classic → Policies. In the top right corner, click Custom Options and select Centralized Policy → Lists.

  • Under Site, click New Site List and create two site lists:

    Name Site IDs
    ux2-dc 110
    ux2-branches 120-199

  • In the top right corner, click Custom Options and select Centralized Policy → Topology. Click … next to the policy name and select Edit.

  • In the TLOC sequence, click Sequence Rule and add a rule that matches site list ux2-dc with action Accept. Click Save Match and Actions.

  • On the left, switch from TLOC to Route. Click Sequence Rule and add a rule that matches site list ux2-dc with action Accept. Click Save Match and Actions.

  • Click Save Control Policy. In the pop-up window, click Activate.

  • Click Next and preview the CLI to see the differences. Then click Configure Devices and wait until the policy update succeeds.
