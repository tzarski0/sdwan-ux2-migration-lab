Step 4: Define the UX 2.0 Topology Policy¶

In this step you build the same hub-and-spoke policy as in UX 1.0, this time as a UX 2.0 topology policy. The logic doesn't change: branches only learn TLOCs and routes from the DC, and everything else is rejected. What changes is which sites it applies to: the new branch site IDs (121-123) instead of the old ones (20-99).

UX 1.0 policy vs UX 2.0 topology¶

UX 1.0 branches-hub-and-spoke UX 2.0 branches-hub-and-spoke-v2
Where it's configured Centralized policy (Classic) Configuration → Topology
Applies to (who) apply-policy site-list branches (site IDs 20-99) Outbound sites: hierarchy group branches (Bergen 121, Tromso 122, Trondheim 123)
Accepts (what) match site-list dc (10) and, after Step 3, ux2-dc (110) Match sites: SITE_10 (10) and dc (110)
Default action Reject Reject

The two policies cover different branches and never overlap:

  • A branch that is still on UX 1.0 (site ID 21-23) is in site list branches, so it gets the UX 1.0 policy.
  • A branch that has been migrated (site ID 121-123) is in hierarchy group branches, so it gets the UX 2.0 topology policy.

Moving a branch from one policy to the other only takes a change of its site ID, which happens when it is deployed with the configuration group in Step 6.

Why do the two policies use different site IDs?

  • A site can't be covered by both policies at the same time. If the UX 1.0 policy and the UX 2.0 topology both applied to the same site ID, the Controllers would have two conflicting policies for that site.
  • The UX 1.0 policy can't simply be deactivated first. That would leave the network without any hub-and-spoke policy until the UX 2.0 topology is activated, so branches would learn routes from each other during that gap.

Giving migrated sites new site IDs avoids both problems. Each site is covered by exactly one policy at all times, and sites move to UX 2.0 one at a time.

Why match both DC sites?

Like the updated UX 1.0 policy, the topology accepts the DC at both its old site ID (SITE_10) and its new one (dc, 110). That way it works no matter whether the DC routers have already been migrated or not, and it stays correct if the DC has to be rolled back.

Tasks¶

  • Go to Configuration → Topology and click Create Topology.

  • Enter a topology name and click Create.

  • Under Add Topology, select Custom.

  • Enter the name branches-hub-and-spoke-v2. Under Outbound Sites, click Add Sites, select group branches and click Save.

  • Click Add Rules. In the first rule, change Type to TLOC, match sites dc and SITE_10, and set the action to Accept. Click Save Match and Actions.

  • Click Add Rules again. In this rule, set Type to Route, match sites dc and SITE_10, and set the action to Accept. Click Save Match and Actions.

  • Confirm the policy looks like the screenshot below, then click Save.

  • Click Close in the bottom right corner. Then click … next to the policy name and select Activate.

  • Preview the CLI to see the differences. Click Deploy, then View Deployment Status, and wait until the policy update succeeds.

No effect yet

No routers are at sites Bergen, Tromso or Trondheim yet, so this policy has no effect on traffic until the branches are migrated in Step 6.
